# Slice zero acceptance

`run.sh` is the cross-cutting acceptance executable; `evals/bindings/acceptance.json` binds its checks to stable `scr:` and `alr:` evals. It does not provision a world or create another payment. The selected-stack owner first creates the company through the public provisioning door, pays one invoice through the v4 path, and exports a fixture for that same world. The runner must execute acceptance after this fixture is ready, not concurrently with destructive journey steps.

Set `CAPXUL_ACCEPTANCE_FIXTURE` to a local JSON file conforming to `Fixture` in `fixture.ts`. Cookie jars and secrets stay outside git. All endpoints must be HTTP loopback; `disposable:true` and a non-`main` world are mandatory before any seed runs. `cookieJar` is a Netscape jar for the named hat holder (not Administrator), relative to the fixture file. `CAPXUL_SECRET` must match Core's operator diagnostic signing secret. Commands are executable-plus-arguments arrays, run from the repository root with inherited environment and suppressed output, never shell-expanded or copied into evidence.

The fixture names the exact invoice, Payment Entry, transaction, Safe, asset and accounting account. Slice zero intentionally uses cent-exact USD accounting and six-decimal test USDC at par. This is not a multi-currency or Harbourline acceptance gate. The source reader fixes an Anvil block cutoff and refuses chain movement during the reads. It requires the selected successful transaction receipt at/before that cutoff to contain exactly one token transfer from the Safe, with the expected amount and the invoice supplier's persisted wallet as recipient. A matching aggregate balance or application hash alone cannot prove this payment. It also compares invoice allocation, double-entry posting, founder-funded Safe ledger balance and Trial Balance against the chain, then checks the actual rendered form controls and report. Missing fields and missing ledger trace columns fail; an API document is not a screenshot.

The fixture's `load` command must perform a real read/replay operation and fail if it does not complete. Provide actual reversible seed/repair commands for:

- `indexer_unready`: stop Ponder (or break its database/RPC connection); repair restarts it and waits for catch-up.
- `delivery_stuck`: hold a real due event unacknowledged by making the disposable site's endpoint unavailable; keep it unavailable for over 300 seconds. Repair restores delivery and waits for an explicit applied/duplicate acknowledgement. Do not merely backdate an unrelated metric.
- `money_event_parked`: make an actual money-event application fail or become unresolved/unmatched; retain its key and reason. Repair fixes the cause and retries/reconciles that event. Do not plant a non-money hat fault and call it a money fault.

Every seed has a repair in `finally`, including a partly failed seed. A bad healthy baseline stops seeding. Faults are serial; the expected alert must be the only active alert on successive observations. This proves the local authenticated operator alert surface, **not hosted paging delivery**. The original payment's ledger rows must remain unchanged after the faults.

Core's HMAC `POST /admin/alerts {org}` must return an ISO **host-time** `observedAt` and exactly one `{id,active,reason,observedAt}` row for each of those IDs. Index diagnostics include numeric-or-null `head`, `chainHead` and ISO `lastAdvanceAt`; delivery includes `pending`, `oldestDueAt`, `events:[{event_key,seq,last_error}]`; parked money includes `events:[{event_key,kind,reason}]`. Times are ISO host-time; unavailable or inconsistent heads require an active index alert, and no pending delivery means `oldestDueAt:null`. The checker independently compares active flags with due age and parked events. Observations older than 15 seconds, missing/duplicate rows, unknown issues and absent reasons fail closed. Quiet means three successful load operations with all three alerts inactive, not an idle/missing monitor. Firing is observed within 330 seconds; repairs must return all alerts to quiet within 60 seconds. The blueprint's generic RPC/process alert obligations are not silently credited by these three money-path checks.

Run the slice's explicit requested eval IDs with `--world slice-zero --environment <environment.json>`; the fixture and environment must both name the actual disposable `slice-zero` world. Do not use `all` to pretend the skeleton's `main` and selected stack share a world. The stable harness filters world constraints to scripts with requested evals, so this binding does not restrict unrelated `main` runs.

The harness passes `CAPXUL_EVAL_RUN_DIR`. Acceptance requires its running `receipt.json` to name `postgres-ponder-erpnext-v4`, `storage:postgres`, `indexer:ponder` and the fixture world, plus a successful Core `/ready`. It writes `acceptance/sources.json`, `acceptance/after.json`, `acceptance/alerts.jsonl`, `acceptance/dom.jsonl`, targeted 2× PNG captures, and `screens.json` entries `{screen,path,source,assertion:"source-equality"}` with run-relative paths. The stable harness collects that manifest into the final receipt. Standalone invocation without that receipt fails every check explicitly; old skeleton passes cannot satisfy this gate. Known secret environment values are redacted from stored alert diagnostics and check lines.

`acceptance.test.ts` validates the accounting controls and the authenticated HTTP/fault orchestration contract using an explicitly simulated server. It does **not** score slice zero or prove the ERPNext/Ponder integration. These 13 evals are the acceptance-owned floor, not the complete slice requirement: the slicer's `sliceZeroRequired(blueprint)` also includes the applicable L1, journey and funnel claims. Required real-world screen/alert evals only pass when the selected-stack fixture, diagnostics, public provisioning, ordered delivery, trace rendering and repairs are all available. Snapshot/restore proof belongs to the world owner; these checks preserve the original payment through alert faults, not a whole-world backup.
