# Accounts runtime

`door.ts` exports permanent mailbox admission, source reads, eligibility and personal Safe setup transitions. Apply `accounts/schema.sql` after Access and common outbox. Every mutation uses the existing caller-owned worker Sql and authoritative numeric world time, never a nested checkout/commit. `admit(sql,{email,via,ref},trace,now)` is for invitations, escrow money waiting and FDE guest authority facts. The caller checks that authority first; admission and the originating fact commit or roll back together. A repeated admission changes nothing. `admitWave(sql,{emails,by},trace,now)` is `accounts.admission.admit`: at most 200 strings, a nonblank operator label, one caller transaction, `{admitted,already,invalid}` with normalized mailboxes (sorted lock order). Each mailbox is admitted `operator:<by>`: a waiting entry `admit`s, an unknown mailbox is born `admit_unlisted` with `joined_via:'operator'`, and an attributed referral moves to `admitted` with its event. The mount must verify the deployment's operator key before calling it; no person session reaches it. Public individual waitlist/referral operations remain parked by `cut.individuals-parked`. `migrateAccess(sql)` then `migrateAccounts(sql)` are the world-creation migrations, after the common outbox and before Payments.

Notices reads `readAdmissionForEvent(sql,entityId)` using the committed outbox envelope's opaque entity ID, including pre-principal/unlisted mailboxes. The result includes `mailbox`, `admitted_by`, `referrer_email` and `referral_rewarded_with_invite`. Events contain only the declared transition props, never a mailbox or fictitious organization. The private source-key table is routing metadata, not an event transport. Principal reads are Access-owned; Party names are Parties-owned.

`startSetup` requires a real authenticated person, Parties profile guard, admission or beta gate and valid signer. It changes only setup state, not the chain or Party directory. `observeClaim(sql,personId,{chainId,finalityDepth},trace,now)` uses Shared's same-Sql indexed claim reader, which checks actual occurrence, readiness/finality and current deployed threshold-one sole ownership in one snapshot. Chain/finality are deployment config, never HTTP input. A recorded transaction hash must match; adoption without one still requires the original indexed occurrence. Missing/lagging proof returns the unchanged claiming row, with no event or synthetic hash/block/time. An unready/unavailable/malformed provider refuses through `IndexerError.code`. The claim transition records the occurrence's transaction hash, block and chain time; `updated_at`/event time remain authoritative world time. No separate `readIndexerHead` can combine a different checkpoint with this admission. `finishSetup` requires the collection owner's ended-approval proof. These transitions are **not** a complete durable claim workflow: service-signer scheduling, receipt recovery, Ponder resumption, welcome funding and escrow/approval orchestration still require actual integration. Do not give them workflow/binding credit before that path runs.

`routeAccounts(sql,path,input,bearer,services,now)` exports the POST adapter for `/accounts/setup/start` (`{signer}` → `{safe,status,attempt}`), `/accounts/setup/lifecycle` (`{personId?}` → `{lifecycle}`) and `/accounts/setup/check` (`{}` → `{setupState,setupUrl,next,safe,claimed,collected}`). It authenticates the real bearer on the same Sql and refuses agents or another person's lifecycle. Services supply the trusted catalogue, Companies House, setup URL and actual Parties profile guard. Lifecycle refuses missing profiles/setup; check gives the setup link instead and maps recorded chain refusals to their safe codes. Reads never start work. Runtime owns the HTTP error mapping and mounting, and must resume the durable workflow after each committed start; this adapter is not evidence that scheduling, signer sending or collection is composed.

Native claim proof: `packages/backend/test/accounts-claim.pg.ts` runs on a seeded disposable Postgres/Ponder/v4 world (the `indexed-claim.pg.ts` environment plus restricted `DATABASE_URL`/`WORKER_DATABASE_URL`) and drives public sign-in, setup start and `observeClaim` through unclaimed, unreached-finality and indexed owner-swap controls before the real occurrence admits the transition.

Native regression: provision an isolated Postgres database named `/access_*` and an isolated Anvil loaded from the committed `contracts/state/core.json`, then run `CAPXUL_DISPOSABLE=true ACCESS_TEST_ADMIN_URL=... ACCESS_TEST_RPC_URL=... node --experimental-strip-types --no-warnings --test packages/backend/test/access-accounts.test.ts`. If `capxul_core` or `capxul_worker` already exists, supply its existing connection URL as `ACCESS_TEST_TENANT` or `ACCESS_TEST_WORKER`, respectively, targeting that same disposable database; otherwise setup refuses before any writes. Only missing roles are created with fresh credentials; existing role passwords are never altered. The chain control creates an actual Safe-owned AgentOwner account and proves/rejects signed challenges against its real ownership; it is not a public actor fixture or claim sender. The in-memory Mail and profile guard are labeled component controls, not public/provider acceptance. No selected-stack claim follows from these tests.
