# Roadmap for the rebuild line (`master`)

Agreed with Aaron on 13 November 2026. This page is the plan this line sticks to. It changes only when Aaron agrees a
change, and the change is written here with its date.

**Goal.** Capxul's own company runs on Capxul.

## What was decided on 13 November 2026

| Decision | In plain words |
|---|---|
| The blueprint is Effect code | An operation, its errors, its events and its logs are Effect declarations that the product imports. The server does not compile until every declared operation has a handler. The old records under `blueprint/` are reference, ported one journey at a time. |
| Three kinds of check | The compiler (shapes, error codes, a handler exists). A generic runner on every scenario (declared events sent, spans and logs present, speed). Written scenarios that run through the door against a world. Internals are the code's business and are covered by package tests. |
| The scenario author is not the builder | A scenario is written before the build by a different agent, and CI rejects one that already passes against an empty handler. |
| Measurement is part of the contract | Every proven run stores timings and outcomes per operation, so speed and cost are climbed as well as correctness. |
| The world is the unit | All companies on one chain with one clock and one record. People, agents, tests and deployments enter through a named world. Three grades: private, shared, real. |
| Infrastructure is Alchemy | One stack per world, deployed many times, borrowing a platform stack. `capxul world create` is a deploy. |
| Hosting | Cloudflare for compute, one Neon branch per world for its one database (app data and the index together), one server for the Frappe bench only. The bench server is an AWS EC2 machine with no inbound traffic, and sites reach it through a Cloudflare Tunnel (Aaron, 13 November 2026). |
| Site creation on a shared bench | Each world holds a token minted when it is created, limited to that world, a site quota and its lifetime. A world whose change touches the Frappe app brings its own bench. |
| Effect everywhere it can be | TypeScript is Effect, measured by two counts that may only fall: non-Effect constructs outside entry files, and non-Effect runtime dependencies. Frappe (Python) and the contracts (Solidity) are outside this. |
| One source for every fact | Agreed 13 November 2026: a speed budget, an error code, an event or a starting world is declared once and imported everywhere else, so two places cannot disagree. A budget is declared only on the operation, says what it measures, and is replaced by measurement; internal calls are measured, never budgeted. The old blueprint let an operation and its own calls declare different budgets with nothing to check them. |
| The old thin line is not canon | Agreed 13 November 2026: the old thin line and blueprint records are a list of behaviours to consider. Each operation is designed again. Payloads and results are fully typed: nothing carries JSON text in a string to be parsed later. |
| Spend cap | Agreed 13 November 2026: at most $10 a day across Cloudflare and Neon. A world is destroyed after its run, so normal use stays far below it. |
| Hono | Accepted 13 November 2026 as a non-Effect dependency while Ponder is used, because Ponder's API file requires it. Looked at again when Ponder is. |
| Test addresses | Agreed 13 November 2026: rehearsals put test addresses under `worlds.abuusama.dev` and are checked over HTTP, because a certificate for a second level needs a paid Cloudflare add-on; every record made is removed after. Real worlds use `capxul.com` once its DNS moves to Cloudflare (Aaron's step), with each site one level under the domain (`<company>-<world>.capxul.com`), so Cloudflare's free certificate covers it. |
| The Amp wave | Agreed 13 November 2026: no more work goes onto `integration/wave-0`. Its open pull requests stay open as the reference for porting; each is closed, with a link to the master pull request and run record that replaced it, once master supersedes it: the world machinery and the thin line's operations at the end of phase 1, every other journey as phase 3 ports it. |
| Scenarios are journeys | Agreed 14 November 2026: a scenario is a journey, a story of operations in order (found a company, pay an employee), not one promise of one operation. Each operation has one set of checks, written once, that run every time it is called in any journey; refusals are steps of a journey. A different agent from the builder writes them, and each journey must fail against empty handlers first. Progress is counted in journeys. |
| One runner, one world | Agreed 14 November 2026 (option B of the speed spikes, `spikes/world-speed`, `spikes/site-speed`): a runner makes one world and keeps it for its run, never one per scenario. A journey starts from a saved starting world by resetting the world in place (database branch, chain, index, Core, sites, one clock), not by building a new one. Until a run measures more, each journey gets its own world, and a journey is 5 to 10 operations. |
| Fleet hub | Agreed 14 November 2026: each kind of world container (chain, bundler, index) is one container application per stage, deployed once; a world is Durable Object names plus a Neon branch on it. Measured: a world's chain, index and bundler answer in 10 to 15 s, against 95 s for a world with its own containers. |
| Sites from a pool | Agreed 14 November 2026: the bench keeps a template site per starting world and gives a world its company sites by claiming a ready copy (1.1 s measured) instead of building one (105 to 120 s); a site is reset in place to a saved point (0.5 to 1.9 s). |
| Slices on integration branches | Agreed 14 November 2026: work on an effort happens on its integration branch `slice/<name>`. Pull requests into a slice run only the fast ladder (`check`, rungs 1 to 5); a slice merges into `master` only when the thin line's journeys pass in CI (`world`), so the full journeys run per slice, not per pull request. |
| Bench templates never change | Agreed 14 November 2026 (option 1B): a template site on a bench is named by its starting world, a fingerprint of the code that builds it, and the world that made it (its site holds that world's company), built once, then only copied from (wording amended with Aaron's agreement, 15 November 2026). No run replaces or drops one; old ones are removed by age. Runs then share the bench without waiting on each other except for a template's first build, and the one-run-at-a-time queue on `world` can be lifted. |
| Phase 3 ordered by parallel safety | Agreed 14 November 2026: phase 3 ports work in the order that can be built safely in parallel, not in the order Capxul's company needs it. Work is cut into units of 3 to 6 operations, each owned by one domain and scored for independence (its starting world exists; no Frappe app change; no new contracts; no outside stand-in; no domain shared within its wave; no unbuilt dependency). A baseline slice first removes the files every operation used to share. Then waves of about 3, 4 and 8 units run at once, and a wave widens only while its measures hold: conflicts in shared files, minutes waiting on the bench, `master`'s world runs green, integration time, the bench's load and the daily spend. |
| One public surface, Frappe where it owns the data | Agreed 14 November 2026: every capability reaches people and agents only through the blueprint's operations, in the SDK and the CLI. Where Frappe already owns the data, as contacts do in the CRM, the operation is Core's and reads or writes the company's Frappe site behind it; Core keeps no second copy. Payroll and HR run through Frappe HR under the hood, and the money and its rules stay on chain: the Agreements contracts and the other on-chain primitives remain. Nobody calls the chain directly; people and agents use Capxul's operations, which drive Frappe, which drives the chain. Where a Frappe record and an on-chain primitive do not match one to one (a payment agreement against invoices, salary slips against an agreement's collections), the mapping is designed and agreed per primitive before its slice is built: which side owns each fact, how their lifecycles line up, the key that reconciles them, and what is parameterised. The old stack's payroll operations are reference only. |
| Every payment settles one sealed document | Agreed 14 November 2026: every on-chain movement of money settles exactly one Frappe document, whose salted hash it carries, so the chain proves which document was paid without showing it. Each payment is recorded against one sealed document, which may be paid in parts and may be overpaid, the surplus sitting on account in the payee's books (reworded with Aaron, 15 November 2026). The contracts that do it are the invoice ledger below. The document is the one Frappe issues natively for the case: the payee's Sales Invoice when the payee has a company, received by the payer as its Purchase Invoice under the same hash; a Salary Slip for an employee; a Purchase Invoice raised by the payer for a payee with no company. A payer may reject an invoice presented under an agreement. Agreements are re-architected so each collection settles its own invoice; the contract changes are allowed. Escrow stays as it is on `master` for now and is revisited later. Design: `primitive-mapping` and `agreements-design` studies of 14 November 2026. |
| No email on chain | Agreed 14 November 2026: an email-derived account is found from a hash of the normalised email under Capxul's namespace, as the old stack does (`infrastructure`, `packages/protocol/src/evm/safe-address.ts`, `computeCapxulSafeSaltNonce`); the email itself never goes on chain. |
| The founder governs the Board | Agreed 15 November 2026: adding a Director and setting the signing threshold are the founder's acts, signed by the founder's own Safe, as the contracts make them (the Shareholders' top hat sits with the founder). Board members do not vote on Board changes. Revisited when a company has more than one shareholder. |
| Who may invite | Agreed 15 November 2026: for now only the founder invites people to a company; a role that grants the right to invite and manage people comes later as its own unit. |
| No streaming pay | Agreed 15 November 2026: per-second streaming of pay is dropped. Pay and agreements settle documents Frappe issues, each paid once on chain. |
| The invoice ledger | Agreed 15 November 2026, in the contracts-from-first-principles thread (`design-notes/invoice-ledger.md` on branch `design/contracts-first-principles`): Payments keeps a running total paid against each sealed invoice, whose id is derived from the payee, token, total, kind and document hash; money reaches an invoice through Budgets, by plain transfer to the invoice's own address, or as a held payment that keeps custody with the payer's email-derived Safe until the full amount arrives; Agreements becomes one thin contract that authorises a payee to collect against their own sealed invoices within a cap per period; an invoice is signed off chain by the issuing member's own Safe, checked against the department's hat. Nothing is built yet. |
| How a feature is built | Agreed 15 November 2026: idea, then decision, then the blueprint delta, then generated artefacts, then journeys and checks written first and failing, then the build, then measured runs, then deploy and watch (`AGENTS.md`, "How a feature is built"). The slice lead signs off a blueprint delta; Aaron agrees only what is a roadmap decision: a new kind of thing with a lifecycle, a new kind of refusal, a contract change, a change to existing behaviour, a new outside dependency. |
| Lifecycles are machines in the blueprint | Agreed 15 November 2026: each thing with a lifecycle that callers see and refusals depend on (an invitation, an approval, a document, a company's site, a world, a budget, later an invoice and a payment) is declared as a machine in its domain: states, a start, moves (each made by an operation's outcome and sending one event), and the refusal from every state a move cannot start from. Machines are flat: no nested or parallel states and no guards that run code; a thing that seems to need parallel states is two machines, and rules about the caller or data belong to the operation. Built from Effect's own parts (Schema for states and events, `Graph` for reachability and the diagram, `Arbitrary` for property tests), not XState (its types are not Effect Schema, so every event would be declared twice, it is a runtime for state in memory, and it would add a non-Effect dependency), nor Effect's `cluster` and `workflow` (runtimes, kept in mind for long waits such as a held payment). Core moves state only through a machine's `step`, the database refuses a state the machine does not have, and the runner checks that each thing's events form a path through its machine. |
| Who may call is declared | Agreed 15 November 2026: roles are declared once in the blueprint, each with where it comes from (a Safe signer, a Seat, a hat, a credential); each operation declares the roles allowed, the company it applies to and the refusal for anyone else. Core works a caller's standing out in one place; the scenario author's suite generates the refusal steps. Rules that depend on data stay declared refusals with their claims. |
| Typed once, by check | Agreed 15 November 2026: two places can disagree today because nothing forbids it. Lint keeps raw schemas in the blueprint's values files and machines, and outside the blueprint in listed edge files only; a declared name is imported, never retyped as a string; everything that crosses into SQL, Python or Solidity is generated, and CI fails when generating again changes a file. Foundry is installed in CI's `check` job and in the agents' cloud environment, so the compiled contracts own their events and functions and every check can build them. A generated SQL constraint never edits an applied migration: a change of states is a new migration. A delta check fails an operation that lacks a declared format, so declaring first is enforced, not advised. |
| Measurement is declared | Agreed 15 November 2026: each operation declares its steps (spans, each of a kind) and its logs (each with a schema); every effectful function of our own code is an `Effect.fn` named by a declared step, which a lint rule enforces; the generic checks fail a call when a declared step is missing while its path ran, and every refusal logs the state or rule that decided it. Library spans are neither required nor forbidden. The evals on journey scores judge the measurement first: a journey passes only when a failed or slow step can be explained from its record alone, by a score first reported from measured runs and then given a threshold from the data, as budgets are. Then they judge the build: tries to green, breakage and recovery, speed and cost per journey over time. |
| Side by side, then flip, then retire | Agreed 15 November 2026: a change to existing behaviour is built beside the old as a new version, its journeys written first; the old journeys stay green; one pull request flips the default once the new version passes every journey; a later one deletes the old. Operations and events carry a version (step 6.1). |
| New formats by a ratchet | Agreed 15 November 2026: new or changed operations use a new format from the day it lands; existing ones move in the same slice where cheap, otherwise sit on an `unmigrated` list that may only shrink; a migration changes no behaviour. New work is born compliant and old work catches up by the ratchet, in parallel, blocking nothing. Breadth's waves (now phase 7) start once phase 3's steps are Done, which needs the lint rules on with their ratchet (3.3), not every old declaration moved. The accounts pilot also needs the declared steps and their lint rule (4.1), not the evals, which land alongside it, measured on its runs; the ledger waits for the pilot. |
| Account identity | Agreed 15 November 2026: a person has one sign-in and one signer everywhere, at the platform, and a world enrols them. Their personal Safe's address is the same in every world of a grade group and account version: the salt is an HMAC of the normalised email, under `capxul:person:v<N>`, with the group's pepper; test worlds (private and shared) use a published pepper, real worlds a secret one that only real Core holds, so nobody but Capxul can find a real person's Safe from an email. Test and real addresses differ. The email never reaches the chain: `claim` takes the salt, not the email (amending "No email on chain", whose claimer today carries the email in its calldata). Companies House sits at one address per account version on every chain. Test worlds run a chain id no public chain uses (today they run Base Sepolia's, 84532), so a test signature cannot be replayed on a public chain. The account version is not the protocol's major version: it changes only when an input of the derivation does (the salt rule, the Safe factory, its singleton or module, the starting owner), and then accounts move side by side, then flip, then retire, through an `account.migrate` operation. The blueprint owns the grade groups, the account version, the normalisation, the chain id per grade and a derivation checked against the contract's. Built as step 5.2. |
| Convergence | The threads on `main` continue until phase 1 passes here. Then `master` becomes the trunk and they move over journey by journey. |

## World lifecycle rules, enforced by code

Learned from worlds piling up on one machine on the other line.

1. A run is one unit: create the world, test, copy the record out, destroy. The destroy happens even when the run fails
   or is interrupted.
2. Every world has an owner and an expiry. What has expired is deleted without anyone remembering to.
3. Keeping a world to debug it is explicit, costs nothing while parked, and is time-limited.
4. Destroy removes everything the world created.
5. A world never lives on the agent's own machine.
6. Timeouts are declared settings, and each step's duration is recorded.

## Steps to the goal

Progress is counted from this table and nothing else. A step is Done only when its Proof is committed on master:
a run record (a JSON file whose `outcome` is `passed`, or a folder of them), a run's transcript, or `check:<command>`
for a rule CI enforces on every pull request (the command must be in `.github/workflows/check.yml`). The dashboard
works the state out from the Proof; a row marked Done without a committed proof is shown as Claimed, not Done.
The time a step was done is worked out too: when the last part of its proof landed on master.
Evidence says in words what the proof shows. `Needs` lists the steps that must be Done first. `Count` is used where a step is
several like things (twelve scenarios); every other step counts as one. `Waits on` names a person when only they can
unblock it.
