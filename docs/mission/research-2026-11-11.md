## A real spend limit for runs

Task r-spend, run r-spend-11110827.

Usage: the repository says the gateway reports no prices [packages/loop/README.md:178]. Its fake streaming gateway emits per-request prompt_tokens, completion_tokens and total_tokens—not dollars [packages/loop/src/modules/capxul/config.test.ts:55]. Stored pi-durable AssistantEntry messages expose usage.input/output to inspection [packages/loop/src/modules/inspect/internal/events.ts:46]. No installed pi-durable source or actual run SQLite records are present in this lane, so live cache/reasoning fields and actual billing cannot be verified here.

Accounting: per-agent spend reads UsageDoc.models and sums cost.total and totalTokens [agents/service.ts:27]; run save() sums the same fields from harness.usage(), overwriting rather than incrementing spentUsd, avoiding replay double-counting [runs/service.ts:33]. Gateway model definitions supply no cost [capxul/internal/config.ts:130]; modelsFrom therefore installs zero input/output/cacheRead/cacheWrite rates [agents/internal/models.ts:13]. Consequently reported tokens do not produce money spend.

Enforcement: --budget-usd becomes opts.budgetUsd [main.ts:35]. Only before an agent step, left = budget − spentUsd is checked, and only when spentUsd > 0; each agent separately has maxTurns:80 and a timeout [capxul/service.ts:73,88]. The running conversation is not money-monitored; zero budgets also bypass that check. save() runs at step boundaries, not after every request [runs/service.ts:43].

Smallest credible change: configure authoritative model rates using the existing cost fields, then pass a run-wide budget check into ask's existing wait/abort loop [agents/service.ts:55], recomputing durable aggregate usage, aborting active conversations and terminating the run with a budget reason at spent >= budget; check before submissions/retries too. Reject missing rates and invalid budgets rather than treating unknown cost as free. This is priced-token accounting, not verified invoice spend. Post-request accounting can overshoot by in-flight requests; a strict dollar ceiling additionally needs pre-request reservations/output bounds or gateway enforcement.

**Recommendation.** Implement priced durable usage plus run-wide abort enforcement and restart/concurrency tests before the five-agent ramp, explicitly labeling estimates and requiring gateway billing or reservations for a strict real-money ceiling.

## Alerts when a run needs Aaron

Task r-alerts, run r-alerts-11110827.

Existing signals: `loop watch` polls every 2s, baselines silently on startup and considers the last 24h; it prints starts, refusals, model failures, unhealthy refusal rates, status changes (including blocked/failed/stopped/dead) and supersession. It is terminal output, not delivered alerts, and restarting it misses existing problems [capxul/service.ts:232; inspect/internal/changes.ts:10]. The host offers Chord `loop.runs` v2 at `/runs/ws`: full run state then diffs, refreshed every 1.5s, plus stop/note methods—not a durable alert queue. `/runs/summary.json` is a simpler read-only input [host/service.ts:41,62; host/types.ts:50]. Neither contains the portal question inbox.

Portal: Runs attaches live, reconnects after 4s, and shows blockers, findings and builder questions; a blocked run is explicitly for coordinator triage, not necessarily Aaron. Questions combines waiting blueprint decisions and plan needs assigned to the owner [live.ts:33; Overview.tsx:17; Results.tsx:12; questions.ts:35]. Static pages require regeneration; the Mac portal proxies `/runs/` and is reachable through Tailscale [portal-ops]. There is no outbound delivery in these paths.

Options (engineering/operating costs, not quoted vendor prices): piping watch to a Mac notification is cheapest but loses restart catch-up and owner questions; browser notifications over the websocket add permission/client-lifecycle work and depend on an attached browser; a Mac-side reconciler costs modest implementation plus supervision but works without a page; remote push/email adds credentials, provider dependency, retries and possible fees. Repository evidence establishes neither provider prices nor configured delivery/receipt.

Smallest reliable design: one supervised Mac notifier reads structured run state and the same authoritative owner-inbox inputs, persists pending alerts/deduplication keys, reconciles on startup/reconnect, retries failures and links to Runs/Questions through Tailscale. Batch five-agent noise; alert once per actionable status episode/new question, suppress superseded runs, and keep transient model failures with the coordinator. Local notification is Mac-only; phone delivery needs an approved external channel.

**Recommendation.** Implement the supervised, persistent Mac reconciler with local notifications first, verify restart catch-up and question detection, and add an approved push/email transport if Aaron needs alerts away from the Mac.

## Running agents in a real sandbox

Task r-sandbox, run r-sandbox-11110827.

What exists: the current ruling replaces golden swarmD sandboxes with worktrees and gates (blueprint/shared/swarm.ts:811–827). Neither loop sandbox contains an agent: light starts seeded Anvil on a free port; heavy creates a world/company site against an existing Docker stack (sandbox.ts:16–38). Agents still use NodeExecutionEnv in the runner process (host.ts:11–43). The README explicitly says node/pnpm can bypass the tool filter and real containment needs an OS sandbox around the whole runner (README:128–132).

Untested: heavy is expressly unexercised; it requires the Frappe stack, spikes/skeleton/.env and viem, and uses allocated—not system-discovered free—ports (README:158–163). No sandbox-exec profile, containerized loop launcher or containment proof was found in the repository; availability/behaviour on this Mac therefore remains unverified. The five-agent ramp is a concurrency experiment, not a sandbox test (plan/log.jsonl:340).

Smallest proposed experiment: one builder, LOOP_MAX_AGENTS=1, --sandbox none, with the entire run process and descendants wrapped in a deny-by-default macOS sandbox-exec profile, conditional on checking that this Mac supports it. Permit required runtime/dependency reads, writes only to the disposable checkout/run state/temp, and networking only to the local gateway at 127.0.0.1:8317. Account for SQLite, git metadata, dependency installation, plan claims and the steering socket; run setup/gates/push outside the experimental boundary where necessary rather than widening agent permissions (service.ts:44–57,171–186,143–146). Prove outside-file reads/writes and external connections fail even through node, while edits, model calls, stop/resume and evidence work. This is a design to validate, not a supplied working profile. Containers are an alternative but need a runner image, scoped mounts and gateway connectivity; the existing heavy Docker stack supplies none of that agent isolation.

**Recommendation.** Record the OS-boundary decision, then prove one disposable builder under a whole-process sandbox-exec profile before adding light/heavy services or increasing concurrency, using a container runner if the Mac cannot support the profile.
