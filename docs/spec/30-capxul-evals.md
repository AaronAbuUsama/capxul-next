# Capxul evals

> **Read with the design book.** This spec was written before the design book. Where the two differ,
> the book wins:
> - The eval catalogue is derived by `packages/book` from the target records: `evals.json` of a
>   build. There is no `pnpm eval`. The repository uses npm workspaces, and the harness's command
>   is the build session's to name (B2).
> - Worlds are the named snapshots in `books/target/devnet/worlds.ts`, and a refusal names one in
>   its `given`.
> - `sys:loc` is per concept (`system.size`, `system.layout`). The harness keeps its own budget
>   of 2,000 lines.
> - The harness never targets the old system: it is a reference for behaviour, not a baseline.

**Every claim about Capxul that counts is an eval in this catalog.** The
catalog is generated by `pnpm eval list` from the operation definitions and a
few hand-written files. The runner, `pnpm eval run`, is the harness. Its whole
job is to turn ids into `RunResult`s (see the
[ledger spec](10-swarmd-ledger.md)).

**Line budget: 2,000 lines for the harness**, excluding eval bodies and
worlds. That is an L3 eval: `sys:loc/harness`.

## Id grammar

```
EvalId   = kind ":" subject [ "/" qualifier ]
kind     = acc | ret | ref | evt | spn | bud | doc | des        (L1, an operation)
         | rpc | flw | prc | tbl | trn | wfl | int             (L1, the records below an operation)
         | jrn | fun                                           (L2)
         | sys | inv | env                                     (L3)
         | live                                                (L4)
         | rev | ok                                            (judged: agent / person)
subject  = an operation id ("payment.send"), a journey key ("get_paid"),
           a system subject ("loc/backend"), or a task id ("K-12")
qualifier= an acceptance number, an error code, an event name, a measure
```

Ids are stable. Renumbering acceptance lines is forbidden. A removed line keeps
its number retired, as in the old repo's "the list only shrinks".

## Kinds

**Level 1: one operation.** Every `machine` eval runs through the CLI on a
devnet, as a black box.

| Kind | Example id | Claim | Source | Decider | Evidence |
|---|---|---|---|---|---|
| `acc` | `acc:payment.send/3` | the operation's acceptance line *n* holds | the definition's `acceptance[n]`, with a hand-written eval body | machine | run, plus any declared |
| `ret` | `ret:payment.send` | a success returns exactly the definition's output schema, and `--json` prints it | generated | machine | run |
| `ref` | `ref:payment.send/INSUFFICIENT_FUNDS` | the declared refusal is reachable from its `given`; it returns that code, the declared exit code and the failure shape; nothing changes | generated from `refusals[]`, each with a `given` | machine | run |
| `evt` | `evt:payment.send/payment_transitioned` | the operation sends the declared event, valid against its catalog schema, carrying `trace_id`, once per state change | generated from `events[]` | machine | events |
| `spn` | `spn:payment.send` | the trace has the declared span tree: an operation span, the declared child spans, the required attributes, `outcome` and failure fields on a refusal | generated from `spans` | machine | trace |
| `bud` | `bud:payment.send/p95` | over N runs from a warm world, the system-time p95 stays within budget (p50 likewise); chain confirmation and a person's wait are excluded through span names | generated from `budget` | machine | measure, with measures `{p50_ms, p95_ms, n}` |
| `doc` | `doc:payment.send` | the CLI help, the reference page and the definition agree (generated surfaces are unedited) | generated | machine | run |
| `des` | `des:payment.send` | the definition is complete and consistent with the book record and the old behaviour: every field filled, the refusals cover the book's `refusals`, the events and spans follow the measurement rules | generated | agent: `design-reviewer` | review |

**Level 2: a journey.**

| Kind | Example | Claim | Source | Decider |
|---|---|---|---|---|
| `jrn` | `jrn:get_paid` | the journey's scenario runs end to end on a devnet: every step's operation succeeds in order for the scenario's people | `journeys/<key>.ts`: an ordered list of operation calls with roles | machine |
| `fun` | `fun:get_paid` | every step has a proving event, so the funnel can be derived; running the scenario produces each step's event once, in order, with one `trace_id` per step | generated from the journey and the events | machine |

**Level 3: the system.**

| Example | Claim |
|---|---|
| `sys:loc/<package>` | the package is within its line budget (non-test, non-generated) |
| `sys:suite-time` | every L1 and L2 machine eval runs in ≤ 20 min on one sandbox |
| `sys:bundle/<entry>` | the entry is within its size budget |
| `sys:cold-start` | a backend cold start stays within its budget |
| `sys:cli-start` | `capxul --help` starts within 800 ms of CPU time (as in the old repo) |
| `sys:catalog` | everything emitted is declared, and everything declared is emitted by some eval run |
| `sys:shape` | the folder shape and import rules hold |
| `sys:generated` | the generated files equal what the generator produces from the definitions |
| `sys:p95-regression` | no operation's `bud` p95 rose more than 20% against the `main` ref |

**Level 4: live traffic.** The decider is a machine reading PostHog with
HogQL, through the scout worker's sandbox.

| Example | Claim |
|---|---|
| `live:bud:<op>` | on staging over 7 days, the operation's p95 is within budget (n ≥ 30, otherwise `unverifiable`) |
| `live:err:<op>` | the defect rate is ≤ 0.5%, and refusals stay within their expected classes |
| `live:fun:<journey>` | step conversion is no worse than the 4-week baseline |

**Judged, any level.**

| Example | Decider | Claim |
|---|---|---|
| `rev:K-12` | agent: `reviewer` | the change for task K-12 is correct, minimal and readable, and follows the rules |
| `ok:K-1` | person: `aaron` | the milestone is accepted |

## Which evals are scored

- **Scored:** L1, L2, L3 and L4.
- **Not scored:** L0, which is the project's own unit tests, the
  `runner.gate`. It must pass before a submission reaches a checker.
- **Agent and person evals count toward `done`,** but the scoreboard shows
  them in their own column.

## Where evals come from in the design book

The design book (`50-design-book.md`, code in `packages/book`) derives every eval from records;
nobody writes an eval list by hand. The operation is the frozen unit and keeps its book text; its
implementation is one rpc or one Core SDK flow, and the server and data records below it carry the
rest:

```ts
export const operation_payment_send = defineOperation({
  ...frozenText("payment.send"),               // the old book's text, generated, never retyped
  priority: "critical",
  implementedBy: flow_client_payments_send,    // the Core SDK flow the CLI's one SDK call runs
  acceptance: [                                 // policy P1: claim, what a black-box run observes, the old citation
    { claim: "Sends to a Party's saved destination and returns the Payment in settling.",
      observes: "exit 0; --json payment.status is settling; payment_transitioned to settling on the trace",
      was: ["backend send.test.ts"] },
  ],
  returns: PaymentSchema,
  refusals: [{ error: error_INSUFFICIENT_BALANCE, given: "org-safe-empty", when: "The Safe holds less than the amount." }],
  errors: [error_CLI_USAGE],                    // produced by the CLI command itself
  budget: budget("chain-submit"),               // the class default (policy P5); an override needs why
});
```

Events come from the state machine the implementation drives (one `<machine>_transitioned`
event per machine, policy P7). Spans come from the runtime at each boundary (policy P6); records
list only extra spans. The eval kinds each record yields are in `50-design-book.md`, "Evals".

An `acc` eval body lives next to the operation, as `payment.send.evals.ts`:

```ts
import { evals } from "#evals";

export default evals("payment.send", {
  1: async ({ world, cli, expect }) => {
    const w = await world("org-funded");                          // a named snapshot of the devnet
    const r = await cli(w.alice, ["payment", "send", "--to", w.parties.bob, "--amount", "10", "--json", "--confirm"]);
    expect(r.exit).toBe(0);
    expect(r.json.payment.status).toBe("settling");
  },
  3: async ({ world, cli, expect, read }) => { /* … */ },
});
```

## The harness

The surfaces it gives an eval body:

| Surface | What it does |
|---|---|
| `world(name)` | Restores a named devnet snapshot and returns its handles: people with signed-in CLI homes, Organizations, parties, Safes. A world is built once by a script (`worlds/<name>.ts`), snapshotted, and restored in seconds. **No per-test seeding.** |
| `cli(person, argv, opts?)` | Runs the real `capxul` binary with that person's home. It returns `{exit, json?, stdout, stderr, traceId, durationMs}`. Every call gets a fresh `traceparent`, so its spans and events can be found. |
| `read(person, op, input)` | Calls a read operation, for assertions on state. |
| `observed(traceId)` | Returns the spans and events captured for that trace by the harness's local OTLP collector. It writes to an in-memory store and a file in `EVIDENCE_DIR`, and never reaches PostHog during evals. |
| `expect` | A small assertion helper. A failure message becomes `detail`. |

Generated evals (`ret`, `ref`, `evt`, `spn`, `bud`, `doc`) have no
hand-written body. The harness runs them from the definition, using `given`
worlds for refusals and the `acc:…/1` body as the success path.

**What the harness does not do:**
- store results
- compute status
- compare against history
- decide staleness

**Those belong to the ledger.** The harness prints `RunResult[]` and writes the
evidence files. That is all.

**It never runs against the old system.** Aaron decided on 8 November 2026 that the old system is a
reference for behaviour, not a baseline (`system.frozen-behaviour`; `docs/decisions/README.md`).
When an eval's intent is unclear, read the old code for the behaviour; do not run the eval there.
